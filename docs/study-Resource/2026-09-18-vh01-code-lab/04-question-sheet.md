### F1

`GET /api/v1/public/resources` 进入 `PublicContentController.resources`，它只做参数绑定，把 `ContentKind.RESOURCE` 和查询参数交给 `ContentService.listCatalog`。Service 依次做：`pageSize` 夹取到 1～50；解析模块并确定 kind；校验筛选与状态；`CatalogSort.resolve` 决定本次排序；`CatalogCursor.decode` 解码游标（不匹配就 400）；把筛选字段的类型绑定到对应列；用 `CatalogQuery.selectIds` 生成「取 id 与排序键」的 SQL，`limit` 是 `pageSize + 1`。`JdbcTemplate` 只返回 `id` 和归一化后的 `sort_key`。Service 用多出的那条判断 `hasNext`，截断出原始页，再用 `inOrder` 按 id 回查实体并恢复顺序，随后 `filter(hasPublicSource)` 做来源兜底，最后 `toPublic(item, false)` 转 DTO。`nextCursor` 取原始页最后一条的排序键与 id 编码，响应带回本次生效的 `sort`。

### F2

载荷是 `sort.name() + "|" + key + "|" + id`，整体做 Base64 URL 编码并去掉 `=` 填充，前缀 `c1.`。`decode` 的出口：

| 情况 | 结果 |
|---|---|
| 空值或空白 | 返回 null，等同第一页 |
| Base64 解不开 / 段数不是 3 / id 为空 / sort 名不在枚举 | 400 `CATALOG_CURSOR_INVALID` |
| 载荷里的 sort 与本次请求的 sort 不一致 | 400 `CATALOG_CURSOR_MISMATCH` |
| 26 位 ULID 且本次排序是 `DEFAULT` | 兼容旧游标，`legacy = true`，走 `c.id < ?` |
| 其他任何值 | 400 `CATALOG_CURSOR_INVALID` |

### F3

| 排序 | sort_key 表达式 | ORDER BY |
|---|---|---|
| `DEFAULT` | `coalesce(o.sort_order, 20000)` | `rank asc, c.id desc` |
| `DEADLINE` | `coalesce(cd.deadline_date, rd.deadline_date)` | 空值排最后，然后 `expr asc, c.id desc` |
| `UPDATED` | `c.updated_at` | `c.updated_at desc, c.id desc` |

三种都要加 `c.id desc`，因为排序键可能重复（例如两条内容都没有排名，都落在 20000）。没有次级键时，同一排序键内部的顺序由数据库决定，翻页窗口会漂移，出现重复或漏读。

### F4

第一段：`nextCursor` 取的是**原始排序页**的最后一条，不是可见列表的最后一条。游标表示「我这一窗口已经检查到哪里」，被 `hasPublicSource` 过滤掉的记录也已经被检查过，必须算进窗口；如果取可见列表的最后一条，被过滤掉的行会反复落回下一页窗口，形成反复取回同一批行的空页循环。

第二段：过滤发生在游标计算之后，所以一页返回的可见条目可能少于 `pageSize`，极端情况下 `items` 为空而 `nextCursor` 非空。客户端必须继续跟着 `nextCursor` 请求下一页，直到它为 null；不能把「本页 0 条」当成「没有更多」。当前前端就是按 `nextCursor` 是否存在显示「下一页」。

### F5

`OFFSET` 的语义是「跳过前 N 行」，而 `keyset` 的语义是「从某条记录之后继续」。

并发插入导致重复：用户在第 1 页看到 id 为 10、9 的十条内容后请求 `OFFSET 10`。此时有人插入了一条更新的内容，它排到最前面，原来的候选整体后移一位，`OFFSET 10` 现在指向原来第 10 条，于是这条内容在第 2 页被重复返回。

并发删除导致漏读：用户请求 `OFFSET 10` 之前，排在前面的某条内容被删除（例如下架），候选整体前移一位，`OFFSET 10` 现在指向原来第 12 条，第 11 条被跳过，用户再也看不到它。

另外两个成本：深分页要扫描并丢弃前 N 行，代价随页码线性增长；`keyset` 用排序键比较走索引范围扫描，代价与页码基本无关。

### F6

| 类别 | 例子 | 判断标准 |
|---|---|---|
| 静默夹取 | `pageSize` 夹到 1～50；空字符串归一成 null | 参数是「程度」而非「能力」，夹取后语义仍然成立，用户拿到的结果仍然是他想要的那类 |
| 静默降级 | 模块把 `RESOURCE` 的默认排序配成 `DEADLINE`，实际用 `UPDATED`；`catalog_sort_settings` 读不到时回落 `DEFAULT` | 错在系统内部，用户没有表达过这个诉求，降级能保住可用性 |
| 直接报错 | 用户显式 `sort=deadline` 请求资源列表（`CATALOG_SORT_UNSUPPORTED`）；只给 `filterKey` 不给 `filterValue`（`CONTENT_FILTER_INCOMPLETE`）；排序名不存在（`CATALOG_SORT_INVALID`） | 用户能感知的能力缺失或参数自相矛盾，必须报错，否则他会以为自己拿到了想要的结果 |

### F7

写入路径有 `requireAllowed`，读取路径还有 `hasPublicSource`，注释写明这是 fail-closed 守卫：历史数据或手工导入的数据可能绕过写时校验，所以读时再判一次，不允许无效来源被公开输出。它拦住的是 `http://`、`localhost`、`.local` 与 `.internal`、私网字面量（含 `100.64/10`、`fc00::/7`、`2001:db8::/32` 等）、带凭据 URL。拦不住的边界是：`sourceUrl` 为空但模块声明允许原创来源、并且 metadata 中 `sourceMode` 为 `ORIGINAL` 时，这条记录会被放行——这是「原创内容没有外链也能公开」的合法路径，不是漏洞。另外该守卫的实现选择「解析异常即不公开」，属于 fail closed。

### F8

列表、首页、相关推荐都传 `includeMedia = false`，媒体为空、行动入口为空、核验为 null；详情传 `true`，才去查媒体、公开行动入口和最新核验。收益是列表页避免逐条聚合查询，不会为了渲染一页卡片打出一串额外查询或对象存储请求；代价是同一个 DTO 出现两种形状，客户端不能假设「列表里有的字段详情里一定也有」，详情接口本身更重。在当前数据集上看不出差异，是因为这 3 条合成内容本来就没有媒体、行动入口和核验记录，两种形状的响应字段集合完全相同；要观察到差异，需要一条带媒体或行动入口的内容。

### I1～I5 要点

- I1：先给结论（keyset + 不透明游标携带 `sort|key|id`），再给机制（`pageSize + 1`、多出的判断 `hasNext`、原始页最后一条生成游标），再给边界（可见性过滤在游标之后、空值排序、显式非法排序报错），最后给证据（`CatalogCursorTest`、`CatalogQueryTest` 与 18082 上的实测响应）。
- I2：多出的那条不进响应；不用 `count(*)` 是因为它要再扫一次连接与模糊匹配，且两次查询之间数据可能变化，`count` 与分页结果可能互相矛盾。
- I3：配置错误属于系统内部问题，降级保可用；用户显式请求不支持的能力属于需求冲突，必须报错。
- I4：404 不泄露存在性；403 的语义是「已认证但被拒绝」，公开访客不满足；文案取舍要主动说明；双层校验是 fail-closed。
- I5：JPQL 难以表达按类型动态选择的排序键与游标比较，所以用受控片段拼接 + 参数绑定；证明次级键必要性可以用同一 `sort_order` 的两条数据翻页，删掉 `c.id desc` 后顺序由数据库决定，页码会漂移。
