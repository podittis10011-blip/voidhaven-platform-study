### F1 要点

普通"联系我们"表单只解决"收到消息"，不解决信任与隐私：谁都能伪造内容、没人能追踪处理进度、联系方式会长期堆在数据库里、受控信息（群二维码、内部联系方式）无法在同一个入口下分层发布。VH-06 用三条机制补齐：**公开写要有幂等与限流**（防重复与滥用）、**公开查要有一次性凭据**（不建账号也能追踪）、**受控读要有短期授权**（同一页面里公开与受控内容分层）。边界：站点只做信息与受控入口，协作发生在站外；不收集学生画像。

### F2 要点

链路见 `01-code-reading-guide.md` 第 0 节。四个横切机制的正确顺序与理由：

1. 容器过滤器层：`NoStoreResponseFilter`（`@Order(MIN_VALUE+10)`）→ 安全过滤链（`-100`）→ `RequestIdFilter`（未指定顺序，默认最低）。注意 `RequestIdFilter` 不是"最先"的那个，这一点很容易背错；
2. `PublicWriteRateLimitInterceptor.preHandle` 在 **Controller 之前**——先挡滥用，避免为无效请求做业务与数据库开销；
3. Bean Validation 与来源策略在 **Controller 内、Service 之前**——fail-fast，不产生垃圾记录；
4. 幂等预留与联系方式加密在 **Service 内**。

不能换的两处：限流必须在业务之前（否则昂贵的路径会被打穿）；联系方式开关检查必须在幂等预留之前（否则失败请求会留下幂等记录）。

### F3 要点

三条件同时成立才可接受：

1. 公开写是**匿名的**，不存在可被借用身份的登录会话，CSRF 的攻击模型（借用户已认证身份发起请求）在这里不成立；
2. 攻击者能造成的后果被**幂等键 + 按网络限流 + 来源策略 + 后台审核**限制：即使灌进来，也只是"待审的垃圾条目"，不会直接公开；
3. 会话 cookie 是 `SameSite=Strict` + 未配置跨域 CORS，浏览器侧的跨站自动携带被大幅削弱。

如果没有幂等键：双击/重试/网络重发会生成重复记录。如果没有限流：单机可以无限灌数据，撑爆后台待办与数据库。

### F4 要点

| 凭据 | 熵 | 库内存储 | 有效期 | 泄露后果 | 能否补救 |
|---|---|---|---|---|---|
| 回执号 `id` | ~122 bit（26 字符） | 明文（主键） | 永久 | 单独泄露无用 | — |
| 查询码 | 256 bit（43 字符） | SHA-256 | 永久 | 可查该事项公开进度 | 只能换新凭据（当前无此接口） |
| 邀请码 | 256 bit | HMAC-SHA256 | 批次 ≤90 天 | 兑换一次 grant 并消耗共享额度 | 撤销批次 |
| 短期 grant | 256 bit | SHA-256 | 默认 30 分钟 | 有效期内读全部受控入口 | 撤销批次即刻失效 |

### F5 要点

```sql
update community_invite_batches set use_count = use_count + 1
 where code_hmac = ?
   and state = 'ACTIVE'
   and valid_from <= current_timestamp(6)
   and expires_at > current_timestamp(6)
   and use_count < max_uses
```

时序：A 命中该行并持有行锁 → B 的同一 UPDATE 被阻塞 → A 提交后 B 重读最新值 → `use_count = 1` 不满足 `< max_uses` → 影响 0 行 → `401`。

不需要分布式锁的原因：**判定与写入在同一条语句、同一行上完成**，互斥由 InnoDB 行锁提供，天然跨实例生效。改成 Java 判断（先 select 再 update）会在两个事务之间留下窗口，导致超发；那种写法才需要额外加锁。

### F6 要点

| 读路径 | 授权来源 | 无 grant | 有 grant | 缓存 |
|---|---|---|---|---|
| `/public/community/entries` | grant 可选 | SQL 里只投影 `PUBLIC` | 含 `COMMUNITY_GATED` 并解密 | `no-store`（路径含 `/community`） |
| `/public/community/media/{id}` | grant 必填 | 400（缺头）/401（无效） | 校验后读对象存储 | `no-store` |
| `/public/content/{id}/gated-actions` | grant 必填 | 400/401 | 读 `published_revision` 的受控行动；非 `OPEN` 返回 `[]` | `no-store`（路径以 `/gated-actions` 结尾） |
| `/public/participation/project-join` | grant 可选 | 只有 `PUBLIC` | 含受控 | `no-store` |

两个 URL 分开的原因：公开二维码的可见性由**内容的公开发布状态**决定，受控二维码的可见性由**grant**决定。两者的失效条件不同，混在一个端点里会让"内容被隐藏"和"授权过期"两种语义纠缠，难以分别测试与追责。

### F7 要点

收：`COPYRIGHT` 必须带联系方式（`CONTACT_REQUIRED`）；`PrivateValueCipher.requireEnabled()` 在幂等预留之前拦住未配置的环境。
存：AES-256-GCM，nonce 12 字节随机，密文 `v1:base64(nonce‖ciphertext‖tag)`，`keyId` 单独一列，**AAD = `SUBMISSION:<id>`**，写入 `private_contact_records.delete_after = now + 180 天`。
读：只有后台接口能读，`reveal` 先解密再写 `PRIVATE_CONTACT_REVEALED` 审计；审计里只记"已查看"，不记明文。
删：`RetentionService` 删除 `delete_after < now()` 的行。删不掉（任务失败）时的后果：数据超期留存，违反 DR-002 的分层留存约定——这也是为什么留存规则不能只写在文档里，必须能被任务和测试验证。

### F8 要点

| | `execute` | `executeSingleDelivery` |
|---|---|---|
| 回放 | 返回首次响应体 | 409 `SENSITIVE_RESULT_NOT_REPLAYABLE` |
| 库内响应 | 真实响应 JSON | `{"state":"DELIVERED_NO_REPLAY"}` |
| 适用 | 后台管理写操作 | 返回值含一次性凭据的公开写 |

公开投稿必须用后者，因为返回值带查询码（等价于密码）。代价：用户如果丢了查询码就无法自助恢复，只能由管理员介入——这是**故意的**安全取舍，答辩时要把这一句说出来。

### F9 要点

| 状态码 | 场景 | `code` 示例 |
|---|---|---|
| 400 | 缺幂等键、字段校验失败、非法来源 URL、同时设置与清除截止时间 | `IDEMPOTENCY_KEY_REQUIRED` / `VALIDATION_FAILED` / `SOURCE_URL_REQUIRED` |
| 401 | 邀请码无效/过期/用尽、grant 无效或过期 | `COMMUNITY_INVITE_INVALID` / `COMMUNITY_GRANT_INVALID` |
| 404 | 查询凭据无效（不区分"回执不存在"与"查询码错误"）、受控内容不可见 | `CASE_QUERY_INVALID` / `CONTENT_NOT_FOUND` |
| 409 | 同键异体、一次性结果重放、版本冲突、事项已被处理 | `IDEMPOTENCY_KEY_REUSED` / `SENSITIVE_RESULT_NOT_REPLAYABLE` / `CASE_VERSION_CONFLICT` |
| 429 | 公开写/查询限流、门禁冷却 | `PUBLIC_WRITE_RATE_LIMITED` / `COMMUNITY_GATE_COOLDOWN` |
| 503 | 联系方式功能未配置、社群入口未启用 | `PRIVATE_CONTACT_DISABLED` / `COMMUNITY_NOT_CONFIGURED` |

查询码错误用 404 而不是 403：403 意味着"我知道这个资源存在，但你没权限"，等于给攻击者一个**存在性预言机**——他可以先枚举出有效回执号，再集中火力猜查询码。统一 404 让"不存在"与"密码错"不可区分。

### F10 要点（三种可选答案，任选三条）

1. **门禁失败计数可能被事务回滚（F-01）**：最小修法是把失败事件写入放到 `REQUIRES_NEW` 独立事务，或给 `verify` 加 `noRollbackFor = ApiException.class`；验证方式是连续输错 9 次并查 `community_gate_events`。
2. **`Retry-After` 与实际窗口不一致（F-02）**：429 一律返回 900 秒，而门禁冷却文案写的是 30 分钟、公开写窗口是 3600 秒。修法是让各限流器把自己的窗口带进异常，由处理器动态写 `Retry-After`。
3. **合作申请有两套后台入口（F-05）**：状态白名单与校验写了两遍，容易漂移。修法是让 `PartnerAccountProvisioningService` 复用 `PublicCaseStates.PARTNER` 与同一套 transition 逻辑，只保留"批准"所需的建号副作用。
4. **`statusQueryEnabled` 写死为 `true`**：能力开关在功能未就绪时会说谎。修法是让它来自配置，与真实可用性一致。
5. **限流拦截用精确路径匹配**：`/submissions/`（多一个斜杠）就绕过拦截。修法是改为规范化路径或前缀匹配 + 显式白名单。

### C1 提纲（30 秒 + 3 分钟）

30 秒：无账号访客提交内容 → 服务端用幂等键去重、按网络限流、校验来源、加密联系方式 → 返回只出现一次的回执号+查询码 → 后台审核并公开结果 → 访客用回执号+查询码查进度；同一套授权机制还支撑社群受控入口。
3 分钟：按 F2 的图讲，每讲完一层补一句"所以这里必须……"（例：幂等必须在业务之前预留、受控数据必须在 SQL 层排除）。
主动暴露的一点：**失败冷却目前可能不生效（F-01）**，并说明你怎么发现的、怎么验证。

### C2 追问链应答要点

- 双击：同键同体 → 第二次被 `executeSingleDelivery` 挡成 409，不会产生第二条；前端应在**表单初始化时**生成幂等键，而不是每次点击新生成。
- 键不同：会真的创建两条，靠限流（8 次/小时）与后台合并处理兜底；说明这是"防重复"而不是"防重复意图"。
- 并发兑换：一条 UPDATE 的 WHERE 判定 + InnoDB 行锁，恰好一人成功。
- 撤销后旧 grant：`requireGrant` JOIN 批次表要求 `state='ACTIVE'`，同时撤销会删除 grant 行，双保险，立刻失效。
- 限流额度回滚：限流走 `REQUIRES_NEW` 独立事务，业务回滚不退额度。

### C3 追问链应答要点

- CSRF：见 F3 三条。
- 伪造 `X-Forwarded-For`：默认不信任；只有直连地址落在受信网段且头是**单值纯数字**时才采用，多跳直接回落。（本地 `local` profile 打开信任是为了穿过 nginx，生产要收紧网段。）
- 枚举：查询码 256 bit，且每次查询都占独立限流额度（60/小时），枚举不可行；再叠加"失败一律 404"不给出存在性信息。
- 密钥轮换：`private-value-keys` 是 `keyId:base64` 的**密钥环**，密文自己带 `key_id`，所以可以"多把钥匙同时在环里"，新增一把设为 current 后旧数据仍可解；production profile 会拒绝本地 keyId。
- 日志：`ApiExceptionHandler` 只在服务端日志里记 `requestId/method/path`，不记请求体；`RetentionService` 与审计只记类型与结论。
